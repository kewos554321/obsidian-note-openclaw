## 台灣房市速報（2026-11-18）

**1. 整體趨勢**
央行選擇性信用管制持續發酵，投資買盤退場，市場回歸自住剛需；六都呈現「量縮價盤整」格局，高總價產品議價空間明顯擴大，但精華區低總價小宅仍有撐。整體處於「買方市場」初期，成交天數拉長。

**2. 值得注意的地區／物件**
- **台中北屯洲際／漢神商圈**：重大建設到位（漢神洲際、巨蛋議題），新案與中古三房平車供給量大，是自住換屋熱區，但需留意同區競品過多、轉手壓力。
- **台北中山、松山、大安租賃物件**：捷運沿線小坪數、可租補、可寵物件詢問度高，反映高房價下「以租代買」與包租代管需求強勁。
- **實價登錄高總價帶**：單價27–46萬/㎡、總價5,700萬～2.9億的11層以上大樓仍有成交，顯示蛋黃區高端自住／置產買盤未斷，但屬個案、非全面性。

**3. 對自住者建議**
現在是「挑貨、議價」的好時機——優先鎖定捷運／建設已到位的生活圈，避開供給爆量的重劃區新案，中古屋議價空間優於預售，可大膽出價、拉長比較期。

**4. 對投資者建議**
短線炒作空間已消失，租金報酬率是唯一硬指標；台北小宅、台中成熟商圈可租補物件較穩，但須精算持有成本（稅、管理費、空置率）。高總價產品流動性差，不宜追高。

**5. 風險提醒**
留意央行是否再祭新管制、以及大量交屋潮區域的賣壓；租賃市場雖熱，但供給也在快速增加，租金成長恐趨緩。

#### 📚 Today's Concept: How to read an earnings report

What it is: An earnings report is a company's quarterly financial disclosure showing revenue, expenses, profit, and guidance for future performance. It includes three core statements (income statement, balance sheet, cash flow) plus management commentary and risk factors.

Why it matters: It's the primary source of truth for whether a business is actually making money and growing, letting you verify or challenge the market's story before you buy or sell.

Example: A company reports revenue of $500M (up 20% YoY), net income of $50M (10% margin), and EPS of $1.00 vs. $0.80 expected. But operating cash flow is only $10M because receivables jumped $60M, and guidance for next quarter is $480M vs. $520M expected. Stock drops 8% despite the "beat" — the cash conversion and weak guidance are the real signals.

Rule of thumb: Always check cash flow from operations against net income; if profits consistently exceed cash generated, treat reported earnings as suspect until you understand why.

#### 🧩 Blind 100 — 235. Lowest Common Ancestor of BST [Trees]
**連結:** https://leetcode.com/problems/lowest-common-ancestor-of-bst/
> 📅 **Today's Daily Challenge:** #3174 Minimum Number of Changes to Make Binary String Beautiful [Medium] — Tags: String — https://leetcode.com/problems/minimum-number-of-changes-to-make-binary-string-beautiful/

**Problem Type:** BST property exploitation / iterative traversal

**Key Insight:** In a BST, the LCA of `p` and `q` is the first node whose value lies between them (inclusive). If both are smaller, go left; if both larger, go right.

**Approach:**
1. Start at `root`.
2. While current node exists:
   - If `p.val` and `q.val` are both `< node.val` → move to `node.left`.
   - If both `>` → move to `node.right`.
   - Otherwise (split point or one equals node) → return `node`.

**Python3 Solution:**
```python
class Solution:
    def lowestCommonAncestor(self, root: 'TreeNode', p: 'TreeNode', q: 'TreeNode') -> 'TreeNode':
        node = root
        lo, hi = min(p.val, q.val), max(p.val, q.val)
        while node:
            if node.val < lo:
                node = node.right
            elif node.val > hi:
                node = node.left
            else:
                return node
```

**Complexity:** Time O(h) | Space O(1) — h is tree height (O(log n) balanced, O(n) skewed).

**Blind 100 Note:** Classic BST-property problem — teaches you to *use* the ordering invariant instead of generic tree recursion. Represents the "exploit BST structure for O(h) search" pattern. Practice next: 98. Validate BST, 230. Kth Smallest in BST, 700. Search in BST, 108. Sorted Array to BST.

**Contest Tips:**
- **Iterative > recursive** here — O(1) space, no recursion limit worries.
- Normalize with `lo, hi = min(...), max(...)` to avoid two separate branch checks.
- Edge case: `p` or `q` equals `root` → loop returns immediately (correct — a node is its own ancestor).
- Don't confuse with general binary tree LCA (236) — that needs post-order recursion; this one does **not**.
- Guaranteed both nodes exist in the tree per constraints, so no null checks needed beyond the loop.

#### 📷 Today's Concept: Post — RAW vs JPEG: Pros and Cons in Practice

**What it is:** RAW files store all the sensor data with no processing baked in, while JPEGs are compressed, processed images ready to share straight out of camera. Think of RAW as a negative you develop later and JPEG as a Polaroid you get immediately.

**Why it matters:** RAW gives you 2-3 stops of recovery in highlights and shadows plus flexible white balance — critical for portraits with tricky skin tones and landscapes with wide dynamic range. JPEG saves time and card space but locks in your exposure and color choices forever.

**How to apply it:**
1. Shoot RAW for portraits and landscapes where you'll edit — the latitude is worth it.
2. Use JPEG (or RAW+JPEG) for street and casual video stills when speed matters.
3. Expose RAW slightly brighter (ETTR) to maximize shadow detail without clipping highlights.
4. Develop a fast RAW workflow — even a 30-second Lightroom preset beats losing recoverable data.
5. For cinematic video, note that picture profiles (S-Log) are the video equivalent of RAW — grade them, don't bake them in.

**Sony A7C tip:** Set Image Quality to "RAW & JPEG" in the first Shooting menu, and assign a custom button to toggle quality so you can switch on the fly. For video, enable Picture Profile 8 (S-Log3) for maximum grading latitude.

**Common mistake:** Shooting JPEG "to save time" and then discovering blown highlights or wrong white balance you can't fix. If you're unsure, shoot RAW+JPEG — storage is cheap, lost shots aren't.

#### 📚 Today's Concept: Message Queues (Kafka vs RabbitMQ)

**What it is:** A message queue is middleware that decouples producers from consumers by buffering messages until they're processed. Kafka is a distributed append-only log for high-throughput event streaming; RabbitMQ is a traditional broker with flexible routing (exchanges, queues, bindings).

**When to use it:** Use Kafka for event streaming, log aggregation, or replayable pipelines (e.g., clickstream analytics feeding multiple consumers). Use RabbitMQ for task queues and complex routing (e.g., order processing with priority/retry/DLQ per service).

**Example:**
```python
# RabbitMQ: work queue, one consumer per message
channel.basic_publish(exchange='', routing_key='orders',
                      body='{"order_id": 42}')

# Kafka: partitioned log, many consumer groups replay independently
producer.send('orders', key=b'42', value=b'{"order_id": 42}')
```

**Gotcha:** Kafka is *not* a drop-in queue — messages aren't deleted on consumption, ordering is per-partition only, and consumer group rebalancing causes pauses. Conversely, RabbitMQ doesn't scale to millions of retained events or support replay; picking the wrong one means fighting the architecture later.

**怎麼做：**
1. 先寫一句「鉤子」（前 3 秒）：用問題、反差或結果畫面抓住人。

5. 把腳本丟進 AI 剪輯工具（如 CapCut 自動字幕、Opus Clip），依段落快速生成初剪。
