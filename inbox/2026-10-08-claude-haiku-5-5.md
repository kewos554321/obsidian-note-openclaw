### 🏠 台灣房市
> `2026-10-08 10:50:03`

#### AI 分析
**1. 整體趨勢**
2026年Q3台灣房市呈「量縮價撐、區域分化」格局：央行信用管制與高利率環境壓抑投資買盤，但剛性自住需求與都更危老題材支撐蛋黃區價格。高總價住宅成交單價仍見每坪百萬以上（如144.7㎡成交單價45.6萬/㎡，換算約150萬/坪），顯示精華地段抗跌，但外圍與老舊產品議價空間明顯擴大。

**2. 值得注意的地區與物件**
- **蛋黃區商辦與捷運宅**：中山、松山區捷運站周邊帷幕辦公大樓、挑高兩房產品租售需求穩定，租金投報率優於住宅。
- **高總價住宅集中特定區**：實價登錄高總價案例多為11層以上電梯大樓，單價27-45萬/㎡（約90-150萬/坪），買方多為換屋族與長期置產。
- **外圍新案與農舍產品**：桃園蘆竹、宜蘭員山電梯農舍、台南安南區店面等，總價門檻低但流動性較差，需留意區域供給量。

**3. 對自住與投資者的建議**
- **自住**：優先鎖定捷運站800公尺內、屋齡20年內電梯大樓，善用賣方讓利空間議價，避免追高外圍新案。
- **投資**：住宅投報率偏低，可轉向蛋黃區商辦、店面或都更危老標的；高總價產品應以長期持有、租金收益為核心，短線進出風險高。
- **風險提醒**：緊盯央行選擇性信用管制與囤房稅2.0後續，外圍區若供給過剩，價格修正壓力大，進場前務必查實價登錄與區域待售量。

#### 📚 Today's Concept: 52-Week High/Low and Moving Averages

What it is: The 52-week high/low is the highest and lowest price a stock traded at over the past year, showing its full range. A moving average smooths price data by averaging the last N days (commonly 50 or 200) into a single line that updates daily.

Why it matters: These tell you where price sits relative to its own history and trend, helping you judge momentum and support/resistance without guessing. A stock near its 52-week high in an uptrend behaves very differently from one near its low.

Example: Suppose XYZ traded between $80 and $140 this year. Today it's $135, above its 200-day moving average of $118 and its 50-day of $128. Price above both averages, with the 50-day above the 200-day, signals a healthy uptrend. If it instead sat at $85, below both averages, that's a downtrend.

Rule of thumb: Buy strength, not just cheapness: stocks near 52-week highs in uptrends often keep rising, while new lows frequently lead lower. Treat a break below the 200-day average as a warning to reassess.

**連結:** https://leetcode.com/problems/valid-parentheses/
> 📅 **Today's Daily Challenge:** #1078 Remove Outermost Parentheses [Easy] — Tags: String, Stack, Bracket Sequences — https://leetcode.com/problems/remove-outermost-parentheses/

# 20. Valid Parentheses

**Problem Type:** Stack / LIFO matching

**Key Insight:** Every closing bracket must match the *most recent* unmatched opening bracket — that's exactly LIFO. Push openers, pop on closers and verify the match.

**Approach:**
1. Map each closer to its opener: `{')':'(', ']':'[', '}':'{'}`.
2. Iterate characters:
   - If opener → push.
   - If closer → stack must be non-empty AND `stack.pop() == map[ch]`, else return `False`.
3. Return `len(stack) == 0` (catches leftover openers like `"((("`).

**Python3 Solution:**
```python
class Solution:
    def isValid(self, s: str) -> bool:
        pairs = {')': '(', ']': '[', '}': '{'}
        stack = []
        for ch in s:
            if ch in pairs:
                if not stack or stack.pop() != pairs[ch]:
                    return False
            else:
                stack.append(ch)
        return not stack
```

**Complexity:** Time O(n) | Space O(n)

**Blind 100 Note:** Canonical **stack** problem — the gateway to all bracket/matching/parsing problems. Represents the "use a stack to track nested structure" pattern. Practice next: *Min Stack*, *Evaluate Reverse Polish Notation*, *Generate Parentheses*, *Daily Temperatures*, *Largest Rectangle in Histogram*.

**Contest Tips:**
- **Edge cases:** empty string (valid), single opener `"("` (invalid), single closer `")"` (invalid — must check `not stack` *before* `pop`).
- **Python trick:** `stack.pop()` on empty raises `IndexError` — always guard with `not stack` first. Alternatively use `stack[-1]` to peek without popping.
- **Common mistake:** forgetting the final `not stack` check — `"((("` would incorrectly return `True`.
- **Micro-opt:** `pairs` dict lookup is O(1); avoid `if/elif` chains for each bracket type.
- **One-liner variant** (less readable, avoid in contests): `return not stack` at the end is the cleanest finish.

#### 📚 Today's Concept: Rate Limiting Algorithms (Token Bucket, Leaky Bucket)

**What it is:** Rate limiting caps how many requests a client can make in a time window, protecting services from overload and abuse. Token Bucket refills tokens at a fixed rate and allows bursts up to bucket size; Leaky Bucket drains requests at a constant rate, smoothing traffic.

**When to use it:** Use Token Bucket when you want to allow short bursts (e.g., a user clicking "refresh" a few times). Use Leaky Bucket when downstream systems need steady, predictable load (e.g., forwarding to a legacy API that chokes on spikes).

**Example:**
```python
# Token Bucket
tokens = min(capacity, tokens + (now - last) * rate)
if tokens >= 1:
    tokens -= 1
    allow()
else:
    reject()  # 429
```

**Gotcha:** Token Bucket is *not* a hard cap — a full bucket lets a client fire `capacity` requests instantly, which can still overwhelm a fragile backend. Also, in distributed systems, per-node buckets don't add up; you need a shared store (Redis) or you'll accidentally allow N× the intended rate.
