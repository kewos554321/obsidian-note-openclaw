## 台灣房市快評（2026-09-23）

**1. 整體趨勢**
央行第七波信用管制持續發酵，投資買盤退場，市場回歸自住剛需；成交量縮但價格鬆動有限，呈現「量縮價盤」格局。高總價物件去化慢，蛋黃區保值、蛋白區議價空間明顯擴大。

**2. 值得注意的地區/物件**
- **台中西屯、南屯**：仰星殿等新案兩房平車仍為小資首選，台灣大道、文心路沿線機能成熟，議價可期。
- **新北三重（徐匯中學站）**：捷運機能＋2房含傢俱電，租轉買需求強，總價帶親民。
- **台北中山、中正（龍江路、濟南路）**：靜巷大樓、忠孝新生商圈，租賃需求穩定，適合長期持有。
- **桃園楊梅**：金店面、創業型產品供給增，但商圈成熟度不足，需留意空置風險。

**3. 對自住者建議**
善用賣方讓利與新青安／租金補貼，優先鎖定捷運沿線、機能成熟的中小坪數（2房含車位），議價從實登最低價往下談，勿追高。

**4. 對投資者建議**
高總價、大坪數產品流動性差，避開；可關注台中、新北捷運宅的穩定租金報酬，但須計入持有稅與管理成本，投報率低於3%者不建議進場。

**5. 風險提醒**
信用管制未鬆綁前，蛋白區與重劃區供給過剩物件恐再修正5–10%，進場前務必查實登、比較同社區近期成交，避免買在相對高點。

#### 📚 Today's Concept: Dollar-Cost Averaging (DCA)

What it is: Dollar-cost averaging is investing a fixed dollar amount at regular intervals regardless of price. You buy more shares when prices are low and fewer when prices are high, automatically.

Why it matters: It removes emotion and timing pressure from investing, which is useful when you cannot predict short-term price swings. It builds discipline and lowers the risk of dumping your entire savings at a market peak.

Example: You invest $500 monthly in a stock. Month 1 price $50, you buy 10 shares. Month 2 price $40, you buy 12.5 shares. Month 3 price $25, you buy 20 shares. Total invested $1,500, total shares 42.5, average cost $35.29. If you had invested all $1,500 at $50, you would own only 30 shares.

Rule of thumb: DCA works best for steady income and long horizons, but it underperforms lump-sum investing in rising markets. Never use it as an excuse to keep uninvested cash sitting idle for years.

#### 🧩 Blind 100 — 45. Jump Game II [Greedy]
**連結:** https://leetcode.com/problems/jump-game-ii/
> 📅 **Today's Daily Challenge:** #1776 Minimum Operations to Reduce X to Zero [Medium] — Tags: Array, Hash Table, Binary Search, Sliding Window, Prefix Sum — https://leetcode.com/problems/minimum-operations-to-reduce-x-to-zero/

# 45. Jump Game II

**Problem Type:** Greedy — BFS-style level expansion (implicit graph)

**Key Insight:** Think of it as BFS on jump ranges. At each "level" (one jump), track the farthest index reachable. When you exhaust the current level's range, you must jump — increment count and extend the boundary to the farthest reachable so far.

**Approach:**
1. If `n == 1`, return 0.
2. Track `jumps = 0`, `cur_end = 0` (end of current jump's reach), `farthest = 0`.
3. Iterate `i` from 0 to `n-2` (don't need last index):
   - Update `farthest = max(farthest, i + nums[i])`.
   - If `i == cur_end`: we've exhausted this jump's range → `jumps += 1`, `cur_end = farthest`. Early exit if `cur_end >= n-1`.
4. Return `jumps`.

**Python3 Solution:**
```python
class Solution:
    def jump(self, nums: List[int]) -> int:
        n = len(nums)
        jumps = cur_end = farthest = 0
        for i in range(n - 1):
            farthest = max(farthest, i + nums[i])
            if i == cur_end:
                jumps += 1
                cur_end = farthest
                if cur_end >= n - 1:
                    break
        return jumps
```

**Complexity:** Time O(n) | Space O(1)

**Blind 100 Note:** Classic greedy/BFS-on-array problem. Teaches the "level boundary" trick — same mental model as BFS on an implicit graph where each index's neighbors are `[i+1, i+nums[i]]`. Related: Jump Game (55), Minimum Number of Taps to Open to Water a Garden (1326), Video Stitching (1024).

**Contest Tips:**
- **Don't** try DP — O(n²) TLEs on large inputs; greedy is the intended O(n).
- Loop to `n-1` (exclusive), not `n` — you never need to jump *from* the last index.
- Edge case: `n == 1` → answer is 0 (loop doesn't run, returns 0 naturally).
- `nums[i] == 0` is fine — the greedy still works because you only jump when forced at `cur_end`.
- Common bug: incrementing `jumps` at the wrong time. Only increment when `i == cur_end` (i.e., you've used up the current jump's reach).
- The early `break` when `cur_end >= n-1` avoids an extra iteration but isn't required for correctness.

#### 📷 Today's Concept: Portrait — Posing Techniques for Flattering Angles

**What it is:** Posing techniques for flattering angles are methods of positioning your subject's body and face relative to the camera to emphasize jawlines, minimize perceived width, and create pleasing lines. It's about directing small adjustments—chin, shoulders, hips—rather than big dramatic poses.

**Why it matters:** A slight angle change can slim the face, add definition, and make a subject look relaxed and confident instead of stiff or "mugshot-flat." It's the difference between a snapshot and a portrait.

**How to apply it:**
1. **Turn the body 30–45°** away from camera, then rotate the face back toward the lens. This slims the torso and creates a natural neck line.
2. **Drop the chin slightly and push the forehead toward the camera** ("turtle" move) to define the jaw and avoid double-chin shadows.
3. **Position the key light side** so the shadow falls on the side of the face turned away—sculpts cheekbones.
4. **Hands: give them a job**—collar, hair, pocket, holding a jacket. Idle hands look awkward.
5. **Shoot slightly above eye level** for most subjects; it flatters and avoids up-nose angles.

**Sony A7C tip:** Use Eye AF (AF-C, Tracking: Eye) with a fast prime like the FE 55mm f/1.8 or 85mm f/1.8—shallow depth of field separates the subject and softens unflattering background lines.

**Common mistake:** Shooting straight-on at eye level with a flat, frontal pose. It widens the face and kills dimension. Fix: always angle the body first, then adjust the face.

#### 📚 Today's Concept: Message Queues (Kafka vs RabbitMQ)

**What it is:** A message queue is middleware that lets services communicate asynchronously by sending messages to a broker instead of calling each other directly. Kafka is a distributed append-only log for high-throughput event streaming; RabbitMQ is a traditional broker with flexible routing (exchanges, queues, acknowledgments).

**When to use it:** Use Kafka for event streaming, replay, and high-volume pipelines (e.g., clickstream analytics, CDC). Use RabbitMQ for task queues, RPC-style work distribution, and complex routing (e.g., sending order emails, background jobs).

**Example:**
```python
# RabbitMQ: one message consumed once (work queue)
channel.basic_publish(exchange='', routing_key='tasks', body='resize:42')

# Kafka: message retained, many consumers read independently
producer.send('clicks', key=b'user1', value=b'page_view')
```

**Gotcha:** Kafka is not a queue — messages aren't deleted on consumption. Consumers track offsets, so "reprocessing" is normal, not a bug. Conversely, don't use RabbitMQ as an event log; once acked, the message is gone. Pick based on whether you need *streaming with replay* (Kafka) or *task dispatch with routing* (RabbitMQ).
