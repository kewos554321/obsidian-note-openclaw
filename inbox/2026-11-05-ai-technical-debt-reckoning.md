## 台灣房市速報（2026-11-05）

**1. 整體趨勢**
央行選擇性信用管制持續發酵，投資買盤退場，市場以自住剛需為主軸，成交量較去年縮減但價格呈「量縮價穩」格局。高總價產品去化放緩，蛋黃區與捷運沿線仍具撐盤力道，蛋白區則出現議價空間擴大的跡象。

**2. 值得注意的地區／物件**
- **台中雙軸**：西屯中科商圈透店（商業用地、店住合一）與西區五權路捷運藍線三角窗店面，具備「捷運建設＋收租」雙題材，藍線動工期是關鍵觀察點。
- **新北二線蛋黃**：三重亞昕淳白水岸3房含車、淡水靜江悅高樓兩房，屬總價帶可控的自住型產品，淡水需留意供給量大的去化壓力。
- **高總價實價揭露**：近期多筆住宅大樓成交單價落在27～46萬/㎡（約9～15萬/坪換算區間視坪數），高總價仍有成交但集中在精華地段，非全面性。

**3. 對自住者建議**
優先鎖定捷運已通車或明確動工路段，避開供給量過大的重劃區；淡水、基隆等低總價區可談空間較大，但須確認社區管理與未來轉手性，議價從實價登錄近期成交下緣切入。

**4. 對投資者建議**
店面型產品（如台中中科、五權路）須精算租金報酬與空置風險，捷運題材發酵前布局、通車後檢視；住宅投資在高利率與管制環境下報酬有限，建議以長期收租、低槓桿為原則，避免追高蛋白區預售。

**5. 風險提醒**
高總價與大坪數產品流動性下降，若持有此類物件宜拉長銷售期；政策面（信用管制、囤房稅）仍是最大變數，進場前先確認貸款成數與持有成本。

#### 📚 Today's Concept: Enterprise Value (EV) and EV/EBITDA

What it is: Enterprise Value is the total cost to acquire a company outright — market cap plus debt minus cash — because a buyer inherits the debt and gets the cash. EV/EBITDA divides that total price by earnings before interest, taxes, depreciation, and amortization, giving a capital-structure-neutral valuation multiple.

Why it matters: It lets you compare companies with wildly different debt loads and cash piles on equal footing, which plain P/E cannot do. Useful when screening acquisition targets or comparing a leveraged firm against a debt-free competitor.

Example: Company A: market cap $800M, debt $400M, cash $100M → EV = $1.1B. EBITDA $100M → EV/EBITDA = 11x. Company B: market cap $1.1B, no debt, cash $50M → EV = $1.05B, EBITDA $100M → 10.5x. Despite very different balance sheets, they trade at similar valuations — P/E would have misled you.

Rule of thumb: Compare EV/EBITDA only within the same industry; a reading well below peers warrants checking why — often heavy capex or cyclical peak earnings inflate EBITDA and make the multiple look deceptively cheap.

#### 🧩 Blind 100 — 49. Group Anagrams [Arrays & Hashing]
**連結:** https://leetcode.com/problems/group-anagrams/
> 📅 **Today's Daily Challenge:** #1486 Find the Distance Value Between Two Arrays [Easy] — Tags: Array, Two Pointers, Binary Search, Sorting — https://leetcode.com/problems/find-the-distance-value-between-two-arrays/

## **Problem Type:** Hash Map / String Bucketing (Counting)

**Key Insight:** Two strings are anagrams iff their character frequency counts are identical. Use a canonical key (sorted string OR 26-length count tuple) to group them in a hash map.

**Approach:**
1. Initialize `groups = defaultdict(list)`.
2. For each string, compute a canonical key:
   - **Option A (simpler):** `tuple(sorted(s))` — O(k log k) per string.
   - **Option B (faster for long strings):** 26-length count tuple — O(k) per string.
3. Append the string to `groups[key]`.
4. Return `list(groups.values())`.

**Python3 Solution:**
```python
from collections import defaultdict

class Solution:
    def groupAnagrams(self, strs: list[str]) -> list[list[str]]:
        groups = defaultdict(list)
        for s in strs:
            # 26-length count tuple as canonical key — O(k) per string
            count = [0] * 26
            for ch in s:
                count[ord(ch) - ord('a')] += 1
            groups[tuple(count)].append(s)
        return list(groups.values())
```

*Alternative one-liner (cleaner, slightly slower for long strings):*
```python
class Solution:
    def groupAnagrams(self, strs: list[str]) -> list[list[str]]:
        groups = defaultdict(list)
        for s in strs:
            groups[tuple(sorted(s))].append(s)
        return list(groups.values())
```

**Complexity:** Time **O(n · k)** (counting) or **O(n · k log k)** (sorting), where n = number of strings, k = max string length | Space **O(n · k)** for storing all strings in the map.

**Blind 100 Note:** Classic "canonical key hashing" problem — teaches you to reduce an equivalence-class problem to a hashable key. This pattern reappears in *Valid Anagram* (242), *Find All Anagrams in a String* (438), *Group Shifted Strings* (249), and *Word Pattern* (290). Master the "design a key → bucket" reflex.

**Contest Tips:**
- **Empty string edge case:** `""` → count tuple of all zeros; works fine, no special handling needed.
- **`defaultdict(list)`** avoids `if key not in map` boilerplate — always use it in contests.
- **Sorting vs counting:** sorting is shorter to write; counting is faster when strings are long. For LeetCode constraints (k ≤ 100), either passes — pick sorting for speed of typing.
- **Don't mutate input** or sort `strs` in place — order within groups doesn't matter, but keep it clean.
- **Return `list(groups.values())`**, not `groups.values()` — LeetCode expects a list.
- Common mistake: using `set(s)` as key — fails for duplicates (e.g., `"aab"` vs `"abb"`).

#### 📷 Today's Concept: Post — LUT Application for Cinematic Color Grades

**What it is:** A LUT (Look-Up Table) is a preset color-mapping file that transforms your footage's colors and contrast into a specific cinematic look. "Post" LUT application means applying it in your editing software rather than baking it in-camera.

**Why it matters:** LUTs give you consistent, filmic color grades in seconds—unifying skin tones, adding teal-and-orange contrast, or emulating film stocks—without hand-grading every clip.

**How to apply it:**
1. Shoot in S-Log3/S-Gamut3.Cine (or HLG) so your footage has gradeable dynamic range.
2. In your editor, first apply a **conversion LUT** (S-Log3 → Rec.709) to normalize the image.
3. Add your **creative LUT** on a second node/adjustment layer at 50–80% intensity.
4. Adjust exposure and white balance *before* the LUT—garbage in, garbage out.
5. Fine-tune with curves and HSL to protect skin tones from going orange or green.

**Sony A7C tip:** Enable **Picture Profile PP8** (S-Log3/S-Gamut3.Cine) and set **Gamma Display Assist** so you can preview a normalized image while shooting—your LUT will match what you saw.

**Common mistake:** Slapping a creative LUT directly onto ungraded Log footage without a conversion LUT first—this crushes shadows and skews colors. Always normalize to Rec.709 before applying the look.

#### 📚 Today's Concept: Vector Databases and Embeddings

**What it is:** A vector database stores high-dimensional numerical embeddings (arrays produced by ML models) and enables fast similarity search via approximate nearest-neighbor algorithms. Embeddings capture semantic meaning, so "similar" means "close in vector space" rather than exact keyword match.

**When to use it:** Use it for semantic search, RAG pipelines, recommendation systems, or deduplication—anywhere you need "find things like this" over unstructured data (text, images, audio). Example: a support chatbot retrieving relevant docs before calling an LLM.

**Example:**
```python
from openai import OpenAI
client = OpenAI()

emb = client.embeddings.create(
    model="text-embedding-3-small",
    input="How do I reset my password?"
).data[0].embedding

# Store in pgvector / Pinecone / Weaviate, then query:
# SELECT * FROM docs ORDER BY embedding <=> %s LIMIT 5;
```

**Gotcha:** Embeddings from different models (or even different versions of the same model) are **not comparable**—mixing them silently breaks similarity search. Also, cosine similarity ≠ relevance: chunking strategy and embedding model choice usually matter more than the database you pick.

#### 🎬 今日主題：剪輯 — BGM 選擇與情緒匹配：免版權音樂來源
**類別：** 剪輯

**是什麼：** BGM 選擇與情緒匹配是指根據影片段落的情緒（如開場興奮、教學專注、結尾溫暖）挑選對應氛圍的音樂。免版權音樂來源則是可合法使用、不會被版權警告的音樂庫。

**為什麼重要：** 音樂直接影響觀眾的情緒與留存率，選錯會讓影片質感掉一階；用錯來源則可能被下架或無法營利。

**怎麼做：**
1. 先剪好畫面，再依段落標記情緒（興奮／平靜／感動）。
2. 用 YouTube 音效庫、Pixabay Music、Epidemic Sound（付費）篩選「免版權」。
3. 試聽時閉眼想像畫面，節奏對不上就換。
4. 同一支片維持 1–2 首主旋律，轉場用淡入淡出。
5. 下載時記錄授權類型，建自己的音樂資料夾分類。

**新手常犯的錯：** 直接用流行歌當 BGM，導致版權警告。避免方式：只從標示「免版權」的來源下載，並保留授權證明。
