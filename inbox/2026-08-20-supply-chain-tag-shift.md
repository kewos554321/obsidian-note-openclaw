#### 📚 Today's Concept: Enterprise Value (EV) and EV/EBITDA

What it is: Enterprise Value (EV) is the total cost to buy a company outright, including its debt and cash. EV = Market Cap + Total Debt - Cash. EV/EBITDA is a valuation multiple that compares that total price to the company’s operating earnings before interest, taxes, depreciation, and amortization.

Why it matters: Market cap ignores debt, so two companies with the same stock price can have wildly different true costs. EV/EBITDA lets you compare companies with different capital structures, making it the go-to metric for M&A and peer valuation.

Example: Company A has 10M shares at $50 (Market Cap = $500M), $200M debt, and $50M cash. EV = $500M + $200M - $50M = $650M. Its EBITDA is $65M, so EV/EBITDA = 10x. Company B also has a $500M market cap but no debt and $100M cash, so EV = $400M. With EBITDA of $50M, its multiple is 8x. Despite identical market caps, B is cheaper per dollar of operating earnings.

Rule of thumb: A multiple under 8x often signals a value or distressed play; above 15x suggests high growth expectations. Warning sign: if EV/EBITDA is low but debt is huge, the company may be cheap for a reason—check interest coverage before buying.

## 110. Balanced Binary Tree

**Problem Type:** Binary Tree / DFS (Post-order traversal)

**Key Insight:** A tree is balanced if the height difference between left and right subtrees is ≤ 1 at EVERY node. We can compute height and check balance in a single post-order traversal, returning `-1` to signal imbalance.

**Approach:**
1. Define a recursive helper `dfs(node)` that returns the height of the subtree or `-1` if unbalanced
2. Base case: `None` node → height 0
3. Recursively get left and right heights
4. If either side is `-1`, propagate `-1` up
5. If `abs(left - right) > 1`, return `-1`
6. Otherwise return `1 + max(left, right)`
7. Final answer: `dfs(root) != -1`

**Python3 Solution:**
```python
class Solution:
    def isBalanced(self, root: Optional[TreeNode]) -> bool:
        def dfs(node):
            if not node:
                return 0
            
            left = dfs(node.left)
            if left == -1:
                return -1
            right = dfs(node.right)
            if right == -1:
                return -1
            
            if abs(left - right) > 1:
                return -1
            return 1 + max(left, right)
        
        return dfs(root) != -1
```

**Complexity:** Time O(n) | Space O(h) where h = tree height (recursion stack)

**Blind 100 Note:** This is a classic tree DFS problem testing post-order traversal. It's on the list because it's a fundamental pattern: computing properties bottom-up while detecting violations. Similar problems: Maximum Depth of Binary Tree, Diameter of Binary Tree, Validate Binary Search Tree (same pattern with different validation logic).

**Contest Tips:**
- **Edge cases:** Empty tree (`root = None`) → `True`; single node → `True`; skewed tree (linked list shape) → `False`
- **Python trick:** Use `-1` as sentinel value instead of returning tuples `(height, balanced)` — cleaner and faster
- **Common mistake:** Checking balance only at root (not recursively) — must check EVERY node
- **Optimization:** Early termination — once `-1` is returned, we stop exploring deeper (pruning)
- **Space note:** Recursion depth = tree height, so worst case O(n) for skewed trees — be aware of stack overflow for very large inputs
- **Alternative:** Can use iterative post-order with stack if recursion depth is a concern, but recursion is fine for LeetCode constraints

#### 📷 Today's Concept: Portrait — Loop Lighting vs Split Lighting

**What it is:** Loop lighting places a small shadow from the nose onto the cheek, angled downward and slightly outward. Split lighting divides the face exactly in half—one side fully lit, the other in deep shadow.

**Why it matters:** Loop is flattering and dimensional, ideal for portraits and beauty work. Split is dramatic and moody, perfect for cinematic or edgy street portraits.

**How to apply it:**
1. **Loop:** Put your key light 30–45° to the side of the subject, slightly above eye level. Adjust until the nose shadow touches the corner of the mouth but doesn’t cross the cheek line.
2. **Split:** Move the key light 90° to the subject’s side, level with their nose. The shadow should split exactly down the center of the face.
3. **Control falloff:** Use a softbox for loop (gentler transition) and a bare speedlight or strip box for split (harder edge).
4. **Check the catchlight:** Ensure the eye on the shadow side still has a glint—if not, add a small white card or reflector.
5. **Shoot tethered or review:** Zoom into the face on your LCD to confirm shadow placement before firing a burst.

**Sony A7C tip:** Use Face/Eye AF in AF-C mode and set the flexible spot to “Tracking: Expand Flexible Spot.” This lets you recompose while keeping focus locked on the eye nearest the light.

**Common mistake:** Placing the light too high for loop, creating a raccoon-eye shadow. Keep the light just above eye level and feather it slightly toward the shadow side.

#### 📚 Today's Concept: Blue-Green vs Canary Deployments

**What it is:**  
Blue-Green runs two identical environments (blue = current, green = new) and switches traffic atomically via a router/load balancer. Canary gradually shifts a small percentage of users to the new version, monitoring metrics before increasing the rollout.

**When to use it:**  
Blue-Green for zero-downtime releases with instant rollback (e.g., a banking app’s monthly update). Canary for risky changes needing real-user validation (e.g., a recommendation algorithm change on a streaming platform).

**Example:**  
Blue-Green:  
```bash
# Switch all traffic from blue to green
kubectl patch service myapp -p '{"spec":{"selector":{"version":"green"}}}'
```  
Canary:  
```yaml
# 5% traffic to canary
spec:
  weights:
  - service: stable
    weight: 95
  - service: canary
    weight: 5
```

**Gotcha:**  
Blue-Green is not “zero risk”—your database schema must be backward-compatible, or the old environment breaks during rollback. Canary’s biggest mistake is treating “no errors” as success; you must compare business metrics (e.g., conversion rate) against the baseline, not just HTTP 200s.
